# Governance

**Kinderspielstadt Los Ämmerles e.V.** is a registered non-profit (*eingetragener Verein*) that runs the Kinderspielstadt camp in Ammerbuch. The software in the [Los-Aemmerles](https://github.com/Los-Aemmerles) GitHub organisation is developed and maintained by volunteers on behalf of the association.

## Roles

| Role | Responsibility |
|------|----------------|
| **Contributors** | Anyone who opens issues, discusses changes, or submits pull requests |
| **Maintainers** | Organisation members with write access who review pull requests, triage issues, and merge approved changes |
| **Board (*Vorstand*)** | Elected association officers who oversee the project strategically and resolve matters that affect the e.V. as a whole |

Maintainers are volunteers; there is no paid support or service-level agreement for open-source contributions.

## Decision-making

**Day-to-day technical decisions** — API shape, library choices, bug fixes, and documentation — are made through pull-request review and issue discussion among active maintainers. Consensus is preferred; when opinions differ, a maintainer may decide after hearing the arguments in the relevant issue or pull request.

**Larger or cross-repository changes** — new major features, breaking API changes, licensing changes, or shifts in supported platforms — should be raised in an issue first so maintainers and, where appropriate, the board can agree on direction before significant implementation work.

**Association-level decisions** — use of the Los Ämmerles name, funding, legal obligations, and production hosting — rest with the **Vorstand** of Kinderspielstadt Los Ämmerles e.V., not with individual contributors.

## Pull requests and merging

1. Contributions follow [CONTRIBUTING.md](https://github.com/Los-Aemmerles/.github/blob/main/CONTRIBUTING.md) in each repository.
2. A maintainer reviews each pull request for correctness, camp-appropriate behaviour, and project conventions.
3. CI checks must pass before merge unless a maintainer documents a justified exception.
4. At least **one maintainer approval** is required to merge into `main`.
5. Maintainers should not merge their own non-trivial changes without another maintainer's review when a second reviewer is available.

Direct pushes to `main` are discouraged; use pull requests so changes stay visible and reviewable.

## Becoming a maintainer

There is no formal application process. Sustained, high-quality contributions — code, reviews, documentation, or issue triage — may lead to an invitation from existing maintainers or the board. New maintainers are added as organisation members with appropriate repository permissions.

## Code of conduct

All participants are expected to follow the association's [code of conduct](https://github.com/Los-Aemmerles/.github/blob/main/CODE_OF_CONDUCT.md). Enforcement contact: [developers@los-aemmerles.org](mailto:developers@los-aemmerles.org).
